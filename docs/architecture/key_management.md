# Key Management

## Overview

Quoodle uses two cryptographic systems: **JWT/JWKS** for user authentication and **Ed25519** for command and message signing. This document covers key lifecycle, storage, and rotation.

## JWT Signing Keys

- **Algorithm:** RS256 (RSA) via JWKS
- **Rotation:** Controlled by `JWTSigner` service in the control plane
- **Publication:** JWKS endpoint at `.well-known/jwks.json`
- **Consumption:** Gateway fetches and caches JWKS, validates `kid` on every request
- **Revocation:** New keys published with `not_before` timestamp; agents must fetch new keys before accepting commands signed with the new `kid`

## Ed25519 Signing Keys

- **Purpose:** Command envelope signing, webhook signing, agent-to-gateway authentication
- **Key pairs per component:**
  - Control plane: signs command envelopes and webhooks
  - Gateway: signs forwarded messages to agents
  - Agent: signs telemetry and command results
  - Kernel guard: verifies commands from agent (uses controller's public key)
- **Generation:** `quoodle-scripts/generate_ed25519_keys.py` produces base64-encoded 64-byte secret keys
- **Storage:** Environment variables (`ED25519_PRIVATE_KEY_B64`, `KERNEL_ED25519_SK_B64`, `KERNEL_CONTROLLER_PUBKEY_B64`)

## Key Storage by Environment

| Environment | Mechanism                                       |
| ----------- | ----------------------------------------------- |
| Local dev   | `.env` files (auto-generated by `setup_dev.sh`) |
| CI          | GitHub Actions secrets                          |
| Kubernetes  | Sealed Secrets / KMS-backed Secret objects      |
| Production  | Cloud KMS (AWS KMS / Azure Key Vault)           |

## Rotation

- JWT keys: rotate via JWKS re-publication; old keys remain valid until `not_before` of the new key
- Ed25519 keys: rotate by deploying new key and pushing revocation event for the old public key
- Device certificates: rotatable via OTA re-enrollment flow
